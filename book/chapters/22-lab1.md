## 22.3 Reproducing

Sign in as Bola. The page shows her ordinary Lagos sign-in at **08:00**.
The seed data puts it at 09:00 Lagos time, which is 08:00 UTC. So the page
is showing the UTC wall-clock time and labelling it as Lagos.

Go one level down. Is the server wrong, or the browser?

```powershell
curl -s http://localhost:5080/api/me/security -H "X-Demo-User: bola.adeyemi@sentinel.dev"
```

```json
"assessedAtUtc":"2026-10-25T16:35:41.5652577Z",
...
"occurredAtUtc":"2026-10-23T08:00:00",
```

There it is, and it is worth slowing down to see it: `assessedAtUtc` ends
in `Z`, and `occurredAtUtc` does **not**. Both are `DateTime` properties on
the same DTO. One has a zone designator and one does not.

## 22.4 Hypotheses

| # | Hypothesis | Cheapest test | Result |
|---|---|---|---|
| H1 | The seed data is wrong | Query the database directly | Ruled out: `SignInAttempts.OccurredAtUtc` is `08:00` (UTC, correct) |
| H2 | The client formats in the wrong zone | Call `formatInZone('2026-10-23T08:00:00Z', 'Africa/Lagos')` | Ruled out: returns 09:00 |
| H3 | The client parses a zone-less string as local time | `new Date('2026-10-23T08:00:00').toISOString()` in a Lagos browser | **Confirmed**: `07:00:00.000Z`, one hour early |
| H4 | The server sends some timestamps without `Z` | Compare the two fields in the raw JSON | **Confirmed**: only values read from the database lack `Z` |

H3 explains the symptom; H4 explains H3. Why do values from the database
lack the `Z` while `assessedAtUtc` (from `IClock`) has it?

`System.Text.Json` writes a `DateTime` according to its `Kind`: `Utc`
gets a `Z`, `Local` gets an offset, and `Unspecified` gets nothing. A value
created by `DateTime.UtcNow` has `Kind = Utc`. A value read from a SQL
Server `datetime2` column has `Kind = Unspecified`, because the column has no
notion of a zone. Something used to stamp `Utc` on values read from the
database, and now does not.

## 22.5 Finding the change

The ticket mentions an "EF Core housekeeping" deploy. The history agrees:

```powershell
git log --oneline -5
git show HEAD~1 --stat
git show HEAD~1 -- src/Sentinel.Infrastructure/Persistence/SentinelDbContext.cs
```

```diff
-    protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder)
-    {
-        configurationBuilder.Properties<DateTime>().HaveConversion<UtcDateTimeConverter>();
-    }
```

The convention looked redundant ("datetime2 already round-trips the
value") and it was removed. It round-trips the *value*; it never
round-tripped the *kind*. `UtcDateTimeConverter.cs` is still in the
repository, now referenced by nothing, which is itself a clue worth
noticing in any investigation: unused code is often the ghost of a removed
fix.

The same commit simplified the client's parser to `new Date(value)`, which
is why the server's change became a visible symptom instead of an error.

Sources consulted (cite these in your log):

- Microsoft Learn, *DateTime.Kind* and *DateTime and DateTimeOffset in
  System.Text.Json*: serialisation depends on `Kind`.
- Microsoft Learn, *EF Core Value Conversions*: `ConfigureConventions` with
  `HaveConversion` applies a converter to every property of a type.
- MDN, *Date.parse()*: date-time strings without an offset are interpreted
  as local time.

## 22.6 The regression tests, then the fix

Write the tests first and watch them fail on the lab branch. At the wire:

[Fact]
public async Task Every_timestamp_on_the_wire_is_utc_with_a_z()

Both pass. Then **defence in depth** on the client: a browser that receives a
zone-less timestamp should say so rather than guess. That is the strict
`parseApiTimestamp` from Chapter 18, with its own test:

```typescript
it('refuses a timestamp with no zone instead of guessing local time', () => {
  const error = vi.spyOn(console, 'error').mockImplementation(() => undefined);

  expect(parseApiTimestamp('2026-10-24T08:00:00')).toBeNull();
  expect(error).toHaveBeenCalledOnce();

  error.mockRestore();

```

Is the client change part of the fix or scope creep? Argue it in your
write-up either way; what matters is that you made the choice on purpose.
The argument for it: the server bug was invisible for days because the
client silently "handled" bad data. A client that refuses bad data turns
the next such bug into an error on first use.

## 22.7 And the London sign-in?

With the times fixed, Bola's history shows Lagos at 09:00 and London at
09:40, both successful, from a Windows laptop and an iPhone respectively.
That is a genuine *impossible travel* finding. The display bug did not
create it; it only made it look stranger. Your reply to support must say
both things clearly: *the times were wrong, we've fixed that; separately,
the London sign-in is real and Bola should change her password now.*
Merging them into "it was a bug, all fine" would be the most harmful
possible outcome of this ticket.

## 22.8 A follow-up the investigation uncovered

While reproducing, `Sentinel.http` showed that `POST /api/sign-ins` with a
zone-less `occurredAt` is accepted and interpreted as **server-local**
time. On a server in Lagos, `09:00` becomes `08:00Z`; on a server in UTC,
it stays `09:00Z`. The contract says a zone is required. Record it as a
follow-up (reject zone-less timestamps with a 400, via a custom
`JsonConverter<DateTimeOffset>`), not as part of today's fix. Knowing what
*not* to fix in an incident is part of the skill.
