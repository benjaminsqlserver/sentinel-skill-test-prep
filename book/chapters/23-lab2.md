## 23.1 Reading the ticket

| Tunde runs integration scripts on his account | That it does not matter | — |

The support agent has done something valuable: **a comparison**. Two other
users in the same campaign show findings, so "the detector is broken" is
unlikely. The question becomes *what is different about Tunde?* and the
ticket answers it in passing: integration scripts.

Support's real question is not "why is the page green?" but **"is Tunde's
account compromised?"** Answer that first, whatever the code does.

## 23.2 Reproducing, and the first clue

```powershell
curl -s http://localhost:5080/api/me/security -H "X-Demo-User: tunde.bakare@sentinel.dev"
```

```json
{"riskLevel":"None","isCompromiseSuspected":false, ... "recentSignIns":[{"occurredAtUtc":"2026-10-18T23:37:33Z", ...
```

The risk is `None`, as reported. But look at `recentSignIns[0]`: the
"most recent" sign-in is **a week old**, and Tunde's scripts sign in every
four hours. The page is not looking at recent history at all.

Check the data directly, to separate "the data is missing" from "the code
is not reading it":

```sql
SELECT COUNT(*), MIN(OccurredAtUtc), MAX(OccurredAtUtc)
FROM SignInAttempts a JOIN Users u ON u.Id = a.UserId
WHERE u.Email = 'tunde.bakare@sentinel.dev';
-- about 550 rows, from 90 days ago to a few hours ago

SELECT OccurredAtUtc, Succeeded, IpAddress FROM SignInAttempts a JOIN Users u ON u.Id = a.UserId
WHERE u.Email = 'tunde.bakare@sentinel.dev' AND a.IpAddress LIKE '145.53.%' ORDER BY OccurredAtUtc;
-- 7 failures and 1 success from Amsterdam, yesterday evening
```

So the attack **is** in the database. Answer for support, already: *yes,
treat Tunde's account as compromised*, a successful sign-in from Amsterdam
followed seven failures. That message can go out now, before the bug is
fixed.

## 23.3 Hypotheses

| # | Hypothesis | Test | Result |
|---|---|---|---|
| H1 | The detector misses this pattern | Unit test: Tunde-like history into `CompromiseDetector.Assess` | Ruled out: High |
| H2 | Findings are acknowledged | `SELECT * FROM FindingAcknowledgements` for Tunde | Ruled out: none |
| H3 | The query loads the wrong attempts | Log the min/max of what `AccountAssessor` loads | **Confirmed**: oldest 500 of ~550 |

The difference between Tunde and the others: **about 550 attempts in 90 days**.
Chen and Bola have about 45. `AccountAssessor` loads at most
`MaxHistory = 500`.

## 23.4 The cause

```csharp
var history = await db.SignInAttempts
    .AsNoTracking()
    .Where(a => a.UserId == userId && a.OccurredAtUtc >= since)
    .OrderBy(a => a.OccurredAtUtc)      // oldest first...
    .Take(MaxHistory)                   // ...then keep 500: the NEWEST are dropped
    .ToListAsync(cancellationToken);
```

`OrderBy` then `Take` keeps the *oldest* 500. For a user with fewer than
500 attempts the order is irrelevant, which is why every other account
worked and why no test failed. The commit that introduced it had a
sensible-sounding reason ("the detector walks history oldest-first, so
let the database sort it"). The detector does want chronological order, and
it sorts its input itself (Chapter 8 said so). The query's order matters
for one thing only: **which rows survive the `Take`**.

You can confirm without a debugger:

```csharp
Console.WriteLine(query.ToQueryString());
// ... ORDER BY [s].[OccurredAtUtc] OFFSET 0 ROWS FETCH NEXT @__p_1 ROWS ONLY
```

## 23.5 The regression test, then the fix

```csharp
[Fact]
public async Task When_history_exceeds_the_cap_the_newest_attempts_are_assessed()
{
    await using var host = await TestHost.CreateAsync(seed: true);
    var tunde = await host.UserIdAsync("tunde.bakare@sentinel.dev");
    var total = await host.Query(db => db.SignInAttempts.CountAsync(a => a.UserId == tunde));
    Assert.True(total > AccountAssessor.MaxHistory, "The seed data must exceed the cap for this test to mean anything.");

    var status = (await host.Send(new GetAccountSecurityStatusQuery(tunde))).Value;

    Assert.Contains(status.Findings, f => f.Kind == "BruteForce" && f.Severity == "High");
}
```

does not exceed the cap, and a future change to the seed data could make it

## 23.6 What made this bug possible

- **A truncation without a test at the limit.** Every cap (`Take`, page
  size, `MaxHistory`) is a boundary, and boundaries get tests on both sides.
- **A comment that described the wrong concern.** The order was justified by
  the detector's needs, which the detector already met itself.
- **Seed data that did not exercise the cap.** Tunde exists *because* of
  this incident; heavy users are real users.

## 23.7 Follow-ups

- Should a user with more than 500 attempts in 90 days be assessed on 500?
  Dropping the oldest baseline can make an old country look "new". Options:
  aggregate the baseline in SQL (distinct countries and devices) and load
  only the last 30 days in full. Record it; do not do it in the incident.
- Alert on accounts whose sign-in rate looks automated: they are the ones
  most likely to have shared credentials.
